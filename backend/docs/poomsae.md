# بک‌اند مسابقات پومسه

پیاده‌سازی نسخهٔ اول: پومسهٔ انفرادی استاندارد، دو فرم، ترتیب اجرای تصادفی، ثبت نمرات و رتبه‌بندی. فرانت‌اند این بخش هنوز پیاده‌سازی نشده است.

## راه‌اندازی

مهاجرت `000007_poomsae.up.sql` همراه مهاجرت‌های معمول با `go run ./cmd/migrate` یا `AUTO_MIGRATE=true` اجرا می‌شود. اجرای مهاجرت باید روی دیتابیس مقصد موردنظر انجام شود. هیچ رده یا قانون امتیازدهی حدسی به مسابقه‌های موجود افزوده نمی‌شود.

مسیر پایه:

```text
/api/v1/organizations/{org}/poomsae-events
```

هدر همهٔ درخواست‌ها: `Authorization: Bearer TOKEN`. درخواست دارای بدنه: `Content-Type: application/json`.

ساخت رویداد بدون نسخه است. ساخت دسته و ویرایش رویداد نیازمند `If-Match: "EVENT_REVISION"` هستند. تمام تغییرات محتویات دسته، حتی افزودن ورزشکار و قرعه، به `If-Match: "DIVISION_REVISION"` نیاز دارند. پاسخ هر تغییر دسته، نسخهٔ جدید را برمی‌گرداند؛ از نسخهٔ قبلی دوباره استفاده نکنید.

فقدان نسخه 428، تعارض نسخه/وضعیت 409، ورودی نامعتبر 400، عدم ورود 401، دسترسی نامجاز 403 و منبع ناموجود 404 است. موفقیت دارای داده 200 است. مطابق قرارداد موجود پروژه ویرایش با **PUT و بدنهٔ کامل** انجام می‌شود؛ PATCH پیاده نشده است.

## ۱. تنظیمات و ساخت رویداد

`GET /api/v1/organizations/{org}/poomsae-settings-options` انواع پشتیبانی‌شده، سیاست تساوی، انتخاب فرم و ۹ الگوی ردهٔ انفرادی برگرفته از تصویر کاربر را برمی‌گرداند. این الگوها فهرست فرم دارند؛ تاریخ تولد باید برای سال همان مسابقه صریح تعیین شود. عنوان رده یا تصویر کوچک، منبع محاسبهٔ خودکار تاریخ تولد نیست.

`POST /poomsae-events`، نمونهٔ بدنه (سقف‌ها صرفاً مثال‌اند، پیش‌فرض سامانه نیستند):

```json
{
  "name": "جام پومسه",
  "date": "2026-10-03",
  "rules": {
    "accuracyMax": "3.00",
    "presentationMax": "7.00",
    "precision": 2,
    "tiePolicy": "shared",
    "formSelection": "division",
    "allowRepeatedForm": false,
    "version": "آیین‌نامه مسابقه ۱۴۰۵"
  }
}
```

تمام تصمیم‌های rules الزامی‌اند. `formSelection` یکی از `division` (دو فرم مشترک دسته) یا `entry` (انتخاب برای هر ورزشکار) است. نسخهٔ فعلی `precision=2` و `tiePolicy=shared` را پشتیبانی می‌کند؛ سیاست ناشناخته رد می‌شود. سقف هر جزء مثبت و حداکثر `9999.99` است.

پاسخ شامل `id`، `name`، `date`، `rules`، `revision` و `createdAt` است. تاریخ و قوانین پس از ایجاد اولین دسته قفل می‌شوند تا تغییرشان، شرایط ورزشکاران و انتخاب فرم‌های ثبت‌شده را باطل نکند؛ نام رویداد قابل اصلاح است.

`GET /poomsae-events?limit=50&offset=0` فهرست خلاصه را برمی‌گرداند. `GET /:event` مشخصات یک رویداد و `PUT /:event` ویرایش آن است. حد limit بین ۱ تا ۲۰۰ است.

## ۲. ساخت دسته

`POST /:event/divisions` با نسخهٔ رویداد:

```json
{
  "name": "زیر ۱۲ سال",
  "competitionType": "individual",
  "gender": "male",
  "belt": "",
  "birthDateFrom": "2015-01-01",
  "birthDateTo": "2020-12-31",
  "allowedFormCodes": [2, 3, 4, 5, 6, 7, 8, 9],
  "form1Code": 2,
  "form2Code": 3
}
```

بازهٔ بالا صرفاً نمونهٔ API است. بازه‌های تولد، میلادی ISO و شامل هر دو مرز هستند. حداقل یکی از دو مرز الزامی است؛ مرز دیگر می‌تواند null باشد. تاریخ شمسی در فرانت‌اند به میلادی تبدیل خواهد شد. هیچ فرمول فرضی محاسبهٔ سن اعمال نمی‌شود.

جنسیت: `male`، `female` یا `mixed`. کمربند خالی یعنی محدودیت کمربند ندارد. فرم‌ها اعداد متمایز ۱ تا ۱۶ هستند و فهرست می‌تواند ناپیوسته باشد. در حالت `division` دو کد فرم الزامی و باید مجاز باشند؛ در حالت `entry` دو کد دسته باید null یا حذف‌شده باشند.

پاسخ ساخت: `{ "division": {...}, "eventRevision": 2 }`. نسخهٔ دسته ابتدا ۱ است. `GET /:event/divisions` فهرست صفحه‌بندی‌شدهٔ تنظیمات دسته‌ها، `GET /:event/divisions/:division` جزئیات کامل و `PUT` همین مسیر ویرایش تنظیمات در وضعیت draft است. ویرایش تنظیمات، شرایط ثبت‌نام‌های موجود را دوباره اعتبارسنجی می‌کند.

## ۳. ورزشکاران

پروفایل ورزشکار با API موجود سازمان ساخته/ویرایش می‌شود: `POST /api/v1/organizations/{org}/athletes`. سپس `POST /:event/divisions/:division/entries` با نسخهٔ دسته:

```json
{
  "athleteId": "UUID_PROFILE",
  "firstName": "علی",
  "lastName": "نمونه",
  "teamName": "باشگاه نمونه",
  "birthDate": "2016-01-01",
  "gender": "male",
  "belt": "",
  "status": "active"
}
```

پروفایل باید فعال و متعلق به همان سازمان باشد؛ تاریخ تولد و جنسیت ثبت‌شدهٔ پروفایل، اگر موجود باشند، باید با ورودی منطبق باشند. تاریخ، جنسیت و کمربند با شرایط دسته تطبیق داده می‌شوند. `status` در ایجاد می‌تواند حذف شود و در آن صورت active است. وضعیت‌های دیگر `absent` و `withdrawn` هستند.

نام، نام خانوادگی و تیم snapshot ثبت‌نام هستند و ویرایششان پروفایل مشترک را تغییر نمی‌دهد. تیم در این نسخه نام نمایشی است و شرکت‌کنندهٔ تیمی محسوب نمی‌شود.

| روش و مسیر زیر دسته | کاربرد |
|---|---|
| `GET /entries?search=...&team=...&limit=50&offset=0` | فهرست `{items,total,revision}`؛ team تطبیق دقیق، search جست‌وجوی نام/نام خانوادگی/تیم |
| `POST /entries` | ثبت‌نام در draft |
| `PUT /entries/:entry` | ویرایش با بدنهٔ کامل و reason در موارد لازم |
| `DELETE /entries/:entry` | حذف فقط پیش از قرعه و پیش از هر سابقهٔ نمره |

هویت پروفایل ثبت‌نام قابل تعویض نیست. بعد از قرعه، مشخصات احراز شرایط قفل می‌شوند؛ برای اصلاح قبل از نمره ابتدا قرعه را با علت باطل کنید. پس از اولین نمره، اصلاح مشخصات نمایشی یا حضور به علت نیاز دارد. بازگرداندن فرد absent/withdrawn به active فقط وقتی مجاز است که در قرعهٔ فعال حضور داشته باشد. دستهٔ نهایی ابتدا باید بازگشایی شود.

## ۴. قرعه و وضعیت‌ها

| روش و مسیر زیر دسته | بدنه / کاربرد |
|---|---|
| `POST /draw` | `{}` برای اولین قرعه؛ `{"reason":"..."}` برای قرعهٔ مجدد |
| `GET /draw` | `{draw,revision}`؛ draw قبل از قرعه null است |
| `POST /invalidate-draw` | `{"reason":"اصلاح فهرست"}`؛ فقط قبل از اولین نمره |
| `POST /finalize` | نهایی‌کردن دسته؛ همهٔ افراد active باید نتیجهٔ کامل داشته باشند |
| `POST /reopen` | `{"reason":"بازبینی"}`؛ با مجوز ویژه |

چرخه: draft → drawn → scoring → finalized. بازگشایی وضعیت را به scoring یا drawn برمی‌گرداند. پرچم `everScored` با پاک‌کردن نمرات پاک نمی‌شود؛ در نتیجه پاک‌کردن نمره راهی برای قرعهٔ مجدد نیست.

قرعه در سرور با Fisher–Yates و `crypto/rand` انجام می‌شود. فقط افراد active وارد می‌شوند؛ صفر نفر خطا و یک نفر جایگاه ۱ دارد. `draw.entryIds` ترتیب قطعی اجراست؛ اندیس صفر، جایگاه اول را نشان می‌دهد. نسخه‌های قبلی قرعه باقی می‌مانند و فقط یک نسخه فعال است. قرعهٔ خودِ فرم‌ها در این نسخه وجود ندارد.

## ۵. ثبت نمره و نتیجه

`PUT /:event/divisions/:division/entries/:entry/scores`:

```json
{
  "form1": { "code": 2, "accuracy": "2.50", "presentation": "6.00" },
  "form2": { "code": 3, "accuracy": "2.60", "presentation": "6.10" },
  "reason": ""
}
```

در حالت فرم مشترک، code قابل حذف است و از تنظیمات دسته گرفته می‌شود؛ کد متناقض رد می‌شود. در حالت فرم فردی، با اولین نمره دو کد فرم مجاز باید مشخص باشند. تکرار فرم طبق `allowRepeatedForm` کنترل می‌شود.

نمرهٔ ورودی رشتهٔ اعشاری انگلیسی حداکثر دو رقم اعشار یا null است. عدد JSON، نمرهٔ منفی، اعشار اضافی، NaN و خارج از سقف رد می‌شوند. تبدیل رقم فارسی وظیفهٔ فرانت‌اند است. محاسبات داخلی integer hundredths هستند؛ مقادیر JSON با دو رقم اعشار ذخیره/نمایش داده می‌شوند.

فرم اول = دقت اول + اجرای اول؛ فرم دوم = دقت دوم + اجرای دوم؛ کل = جمع دو فرم. صفر معتبر است، null یعنی ثبت‌نشده. نتیجهٔ ناقص رتبه ندارد. جمع‌ها در ورودی پذیرفته نمی‌شوند.

PUT نمره، وضعیت کامل چهار جزء را جایگزین می‌کند؛ برای حفظ نمرهٔ قبلی آن را دوباره بفرستید. تکمیل جای خالی دلیل نمی‌خواهد؛ تغییر/پاک‌کردن جزء قبلی یا تغییر فرم دارای نمره به reason نیاز دارد. همهٔ این تغییرات قبل/بعد در تاریخچه ثبت می‌شوند.

پاسخ تغییرات دسته و GET جزئیات، فیلدهای دسته را به همراه این موارد دارد:

- `entries`: ثبت‌نام‌ها و چهار جزء نمره.
- `draws`: تاریخچهٔ قرعه‌ها.
- `results`: ردیف‌های ترتیب اجرا، شامل entry، position، form1Total، form2Total، total و rank؛ rank در results خام null است، رتبهٔ معتبر از standings خوانده شود.
- `standings`: `{revision,final,ranked,unranked}`. ranked با امتیاز نزولی؛ رتبهٔ مساوی مانند ۱، ۲، ۲، ۴. absent، withdrawn و ناقص در unranked هستند.
- `revision`: نسخهٔ جدید برای درخواست بعدی.

`GET /.../standings` مستقیماً همین ساختار standings را برمی‌گرداند. ترتیب نمایش مساوی‌ها با ترتیب قرعه پایدار است؛ قرعه تساوی ورزشی را نمی‌شکند.

## ۶. دادهٔ چاپ و سابقه

`GET /.../sheet?mode=results|blank|standings` snapshot یکپارچهٔ رویداد، تنظیمات دسته، نسخه، قرعه، زمان تولید و ردیف‌ها را برمی‌گرداند. در results ردیف‌ها ترتیب اجرا و رتبهٔ محاسبه‌شده دارند؛ standings ترتیب رتبه دارد؛ blank نمره‌ها و جمع‌ها و رتبه‌ها را خالی می‌کند. فرم‌های مشترک در تنظیمات دسته موجودند.

این endpoint دادهٔ چاپ است؛ ساخت صفحهٔ A4 و PDF به مرحلهٔ فرانت‌اند مربوط می‌شود.

`GET /.../history?limit=50&offset=0` با مجوز `audit.read`، تغییرات همان دسته را با actorId، action، reason، before، after و createdAt برمی‌گرداند. دادهٔ چاپ و رتبه‌بندی از یک snapshot زیر قفل خوانده می‌شوند تا تغییر هم‌زمان خروجی ناسازگار تولید نکند.

## ۷. دسترسی و ذخیره‌سازی

مجوزها: `poomsae.read`، `poomsae.manage`، `poomsae.draw`، `poomsae.score` و `poomsae.override`. مدیر/برگزارکننده مجوزهای کامل و داور مشاهده/ثبت نمره دارند؛ مجوزهای سفارشی موجود خودکار تغییر نمی‌کنند. کوچ و ورزشکار به طور پیش‌فرض دسترسی این بخش ندارند.

Scope عضویت: `poomsaeEventIds` و `poomsaeDivisionIds`. محدودیت هر دو با هم اعمال می‌شود. کاربر محدود به دسته نمی‌تواند رویداد یا دستهٔ جدید بسازد یا تنظیمات رویداد را عوض کند. کاربری که فقط دامنهٔ محدود قدیمی مسابقه/زمین/ایستگاه دارد، به طور خودکار دسترسی سراسری پومسه نمی‌گیرد.

داده‌ها در پنج جدول `poomsae_events`، `poomsae_divisions`، `poomsae_entries`، `poomsae_draws` و `poomsae_change_log` هستند. مطابق الگوی فعلی پروژه، جزئیات ثبت‌نام و نمرات در JSONB همان entry نگهداری می‌شوند؛ ترتیب قرعه نیز در JSONB draw است. این جایگزین هفت جدول پیشنهادی سند برنامه است و از تکثیر منابع امتیاز جلوگیری می‌کند. هویت/سازمان/پروفایل، یکتایی ثبت‌نام و قرعهٔ فعال قید دیتابیس دارند؛ درستی ترتیب قرعه و سقف نمره در سرویس کنترل می‌شود.

هر درخواست در یک تراکنش است؛ ابتدا رویداد سپس دسته قفل می‌شود. این ترتیب برای نسخهٔ اول سادگی و سازگاری snapshot را تأمین می‌کند و تغییرات دسته‌های یک رویداد را نیز سری می‌کند. در صورت نیاز به هم‌زمانی بسیار بالا، کاهش دامنهٔ قفل یک بهینه‌سازی جداگانه خواهد بود.

## ۸. آزمون‌ها

```powershell
go test ./...
go vet ./...
# برای اجرای integration، TEST_DATABASE_URL باید به PostgreSQL آزمایشی اشاره کند.
$env:TEST_DATABASE_URL = 'postgres://postgres@127.0.0.1:55433/postgres?sslmode=disable'
go test ./... -count=1
```

آزمون اتصال برای هر تست schema یکتا می‌سازد و فقط همان را پاک می‌کند. پوشش جدید شامل محاسبهٔ اعشاری، null/zero، مرز تولد، فرم ناپیوسته، هویت ورزشکار، قرعه و سابقه، تساوی، نهایی‌سازی/اصلاح، rollback، جداسازی سازمان، دسترسی داور و ذخیرهٔ هم‌زمان است.

تیمی، دونفره، ابداعی، چند داور، فرم اضافهٔ رفع تساوی، نام‌گذاری رسمی فرم‌ها و تأیید تاریخ‌های ریز تصویر در این نسخه پیاده‌سازی نشده‌اند.
