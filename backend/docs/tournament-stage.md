# مرحلهٔ تورنومنت و ارتباط ورزشکار

این مرحله شامل منطق تورنومنت انفرادی، ارتباط با پروفایل ورزشکار، وزن‌کشی، قرعه‌کشی، ثبت نتیجه، تنظیمات، برنامهٔ دو روزه و شماره‌گذاری است. پیاده‌سازی کامل لیگ، مسابقات تیمی، ورود اطلاعات فایل‌های اپ و صفحه‌های فرانت در این مرحله انجام نشده است. زیرساخت حساب‌ها از مرحلهٔ قبل برای اجرای API موجود است؛ نقش‌های خودخدمت ورزشکار/مربی هنوز به چرخهٔ ثبت‌نام تورنومنت متصل نشده‌اند.

## اختلاف‌های اصلاح‌شده با اپ

| موضوع | رفتار فعلی |
|---|---|
| وزن‌کشی پیش‌فرض | دو نوبت؛ ۲۰۰ گرم ارفاق روی سقف وزن |
| حد پایین | وزن باید از سقف دستهٔ قبلی بیشتر باشد؛ خود مرز به دستهٔ قبلی تعلق دارد |
| دستهٔ مثبت | `+87` یعنی بیشتر از ۸۷؛ ارفاق سقف ندارد |
| پرچم ارفاق | یعنی واقعاً از ارفاق استفاده شده؛ با اجازهٔ استفاده از ارفاق متفاوت است |
| تأیید قدیمی | `weighedIn` قدیمی حفظ می‌شود؛ اگر `weighIn` موجود باشد، وضعیت ساختاری مرجع است |
| سیدبندی | ترتیب ۸ نفر: `1,8,5,4,3,6,7,2`؛ اندیس بازی در هر راند از صفر |
| هم‌تیمی‌ها | بهینه‌سازی برخورد بر اساس مربی و سپس باشگاه، با حفظ چهار سید اول و دریافت‌کنندگان استراحت |
| استراحت | صعود خودکار؛ زمین و ترتیب صفر؛ بدون شمارهٔ بازی قابل‌اجرا |
| شروع قرعه | وزن‌کشی شرکت‌کنندگان همان وزن باید تمام شده باشد |
| ثبت نتیجه | امتیاز و برنده در سرور محاسبه می‌شود؛ برندهٔ ناسازگار با امتیاز رد می‌شود |
| حذف/تغییر وزن | ورزشکار حاضر در براکت قابل حذف نیست؛ تغییر وزن پس از شروع وزن‌کشی رد می‌شود |
| اصلاح نتیجه | نتیجهٔ مرحلهٔ قبلی، در صورت شروع/ثبت نتیجهٔ مرحلهٔ بعد، قفل می‌شود |

این‌ها قواعد پروژه‌اند و ادعای انطباق با آخرین بخشنامهٔ فدراسیون نیستند. محدودیت‌های امتیازدهی و وزن‌کشی در تنظیمات تورنومنت ذخیره می‌شوند.

## ارتباط با ورزشکار

پروفایل عمومی در `athletes` نگهداری می‌شود. ثبت در تورنومنت، رکورد مستقل `tournament_entries` با وزن، رنک، وزن‌کشی و یک نسخه از نام/باشگاه/مربی است. تغییر باشگاه در پروفایل، سابقهٔ تورنومنت قبلی را عوض نمی‌کند.

برای ورزشکار دارای پروفایل:

```json
{"profileId":"UUID ورزشکار","weightCategory":"-58","ranking":1}
```

پروفایل باید فعال، متعلق به همان سازمان و دارای جنسیت منطبق باشد. نام و باشگاه از دیتابیس خوانده می‌شوند. نام/باشگاه ارسالی نمی‌تواند هویت لینک‌شده را جعل کند. هر پروفایل فقط یک ثبت در یک تورنومنت دارد. محاسبهٔ صلاحیت سنی بر اساس تاریخ تولد هنوز به بخشنامهٔ سال/فصل مسابقه نیاز دارد؛ فعلاً ردهٔ سنی تورنومنت فهرست اوزان را تعیین می‌کند.

برای سازگاری با ورود دستی اپ، ثبت بدون `profileId` نیز با `name`، `club`، `weightCategory` و `ranking` ممکن است؛ چنین ثبت‌نامی به حساب یا پروفایل عمومی وصل نیست.

## تنظیمات و صفحهٔ آیندهٔ فرانت

پیشوند تمام مسیرهای زیر:

```text
/api/v1/organizations/{org}
```

`GET /tournament-settings-options` مقدارها و عنوان‌های فارسی گزینه‌ها را می‌دهد. `GET /tournaments/{id}/settings` تنظیمات فعلی و `PUT` همان مسیر، کل تنظیمات جایگزین را دریافت می‌کند. فرانت ابتدا مقدار فعلی را بگیرد، گزینه‌ها را ویرایش کند و سند کامل را بفرستد؛ `PUT` به معنی patch جزئی نیست.

نمونهٔ کامل برای تورنومنت با تاریخ `2026-10-01` و حداقل دو زمین:

```json
{
  "scoring": {
    "pointGap": 15,
    "pointGapFromRound": 1,
    "gamJeomLimitPerRound": 5,
    "roundsToWin": 2,
    "maxRounds": 3
  },
  "weighIn": {"maxAttempts": 2, "toleranceKg": 0.2},
  "draw": {"type": "ranked", "separateTeams": true},
  "schedule": {
    "mode": "split_halves",
    "singleCourt": 1,
    "finalCourtPolicy": "primary",
    "finalCourt": 1,
    "dayAssignment": "alternating",
    "days": [
      {"day": 1, "date": "2026-10-01", "label": "روز اول"},
      {"day": 2, "date": "2026-10-02", "label": "روز دوم"}
    ],
    "categoryDays": {}
  },
  "numbering": {"startAt": 1, "scope": "tournament", "order": "rounds"}
}
```

در `alternating` سرور نگاشت همهٔ اوزان را می‌سازد و در پاسخ برمی‌گرداند: جایگاه اول، سوم، پنجم و ... روز اول؛ جایگاه دوم، چهارم و ... روز دوم. فرد/زوج مربوط به **جایگاه وزن در فهرست همان سن و جنسیت** است، نه عدد کیلوگرم. برای تغییر دستی، `dayAssignment` را `manual` کنید و روز همهٔ اوزان را در `categoryDays` مشخص کنید؛ مثلاً `{"-54":1,"-58":2,...}`. روز دوم می‌تواند غیرمتوالی باشد، ولی باید پس از روز اول باشد.

| حالت | تخصیص |
|---|---|
| `single_court` | همهٔ بازی‌های هر روز روی `singleCourt`؛ حتی فینال |
| `split_halves` | نیمه‌های جدول روی دو زمین کم‌بار؛ مسیر ورزشکار تا پیش از فینال روی همان زمین می‌ماند |
| `balanced` | اوزان بزرگ‌تر ابتدا به زمین کم‌بار تخصیص می‌یابند؛ هر وزن روی یک زمین می‌ماند |

`finalCourtPolicy=primary` فینال را روی زمین اصلی همان وزن برگزار می‌کند. با `fixed` فینال‌ها روی `finalCourt` هستند؛ این انتخاب می‌تواند بار آن زمین را بیشتر و یک جابه‌جایی برای ورزشکار ایجاد کند. در `single_court` زمین منتخب همهٔ بازی‌ها مقدم است.

توازن بر اساس **تعداد بازی قابل‌اجرا**ست. مدت واقعی بازی، فاصلهٔ استراحت، زمان‌بندی دقیقه‌ای و اشتراک فیزیکی زمین بین چند تورنومنت هنوز در این مرحله مدل نشده‌اند؛ بنابراین این روش تضمین ریاضی کوتاه‌ترین زمان پایان نیست. اگر تعداد اوزان از تعداد زمین‌ها کمتر باشد، حالت نگه‌داشتن هر وزن روی یک زمین ممکن است زمین خالی داشته باشد؛ حالت دو نیمه امکان موازی‌سازی بیشتر دارد.

قواعد وزن‌کشی پس از اولین تلاش قفل می‌شوند. قواعد امتیازدهی و برنامه/شماره‌ها پس از شروع اولین بازی قفل می‌شوند. تغییر روز، روش چیدمان یا شماره‌گذاری پیش از شروع، شماره‌های قبلی را پاک می‌کند تا پیش‌نمایش و شماره‌گذاری دوباره انجام شود. حذف نتایج وابسته یا بازنشانی تورنومنتِ شروع‌شده به روند تأیید جداگانه در مرحلهٔ بعد نیاز دارد؛ این API نتایج را خودکار پاک نمی‌کند.

## ترتیب کار و شماره‌گذاری

1. ساخت تورنومنت و ذخیرهٔ تنظیمات.
2. افزودن ورزشکاران و تکمیل وزن‌کشی.
3. قرعهٔ تمام مسابقه یا قرعهٔ جداگانهٔ هر وزن.
4. بررسی `GET /tournaments/{id}/draw-readiness`.
5. `POST /tournaments/{id}/numbering/preview` برای پیش‌نمایش بدون تغییر تورنومنت.
6. `POST /tournaments/{id}/numbering` برای ذخیرهٔ شماره‌ها.
7. شروع بازی و ثبت نتیجه.

`order` جایگاه اجرا در صف زمین و روز است. `matchNumber` شمارهٔ نمایشی است و **هنگام قرعه‌کشی ساخته نمی‌شود**. استراحت‌ها شماره نمی‌گیرند. وزن دارای صفر یا یک ورزشکار تأییدشده در `noContestCategories` گزارش می‌شود و بازی ساختگی تولید نمی‌کند. وزن‌کشی ناتمام یا براکت ساخته‌نشده، شماره‌گذاری را با `409` متوقف می‌کند.

گزینه‌های شماره‌گذاری:

- `startAt`: شمارهٔ شروع.
- `scope=tournament`: شمارهٔ یکتا در کل رویداد؛ روز دوم ادامهٔ روز اول.
- `scope=day`: شروع مجدد در هر روز؛ نمایش روز همراه شماره الزامی است.
- `scope=court_day`: شروع مجدد در هر زمین/روز؛ نمایش روز و زمین همراه شماره الزامی است.
- `order=rounds`: هماهنگ کردن مراحل، با فینال‌ها در انتهای صف‌های مربوط.
- `order=category`: تکمیل هر وزن به ترتیب فهرست اوزان در صف زمین.

در همهٔ حالت‌ها، وابستگی براکت و ترتیب صف زمین رعایت می‌شود. پیش‌نمایش و ثبت روی دادهٔ یکسان شماره‌های یکسان می‌دهند. برای جلوگیری از اعمال پیش‌نمایش قدیمی، مقدار `revision` تورنومنت را به شکل ETag، مثلاً `If-Match: "12"`، بفرستید؛ نسخهٔ قدیمی `409` می‌گیرد. تراکنش و قفل ردیف هم‌زمانی در سطح دیتابیس را مستقل از این هدر کنترل می‌کند.

## مسیرهای اصلی

| روش و مسیر | کاربرد |
|---|---|
| `POST /tournaments` | ساخت؛ `name,date,courts,gender,ageCategory,format` |
| `GET /tournaments` | فهرست با `limit,offset` |
| `GET,PUT,DELETE /tournaments/{id}` | خواندن، ویرایش اطلاعات پایه، حذف |
| `GET,PUT /tournaments/{id}/settings` | تنظیمات |
| `POST /tournaments/{id}/athletes` | افزودن ثبت‌نام |
| `PUT,DELETE /tournaments/{id}/athletes/{entry}` | ویرایش/حذف ثبت‌نام |
| `POST .../athletes/{entry}/weigh-in/preview` | پیش‌نمایش وزن؛ `{"weightKg":58.2}` |
| `POST .../athletes/{entry}/weigh-in` | ثبت تلاش |
| `DELETE .../athletes/{entry}/weigh-in` | بازنشانی پیش از ورود به براکت |
| `POST .../athletes/{entry}/weigh-in/signature` | ثبت مرجع امضا؛ `{"imagePath":"..."}` |
| `DELETE .../athletes/{entry}/weigh-in/signature` | پاک کردن مرجع امضا |
| `POST /tournaments/{id}/draw` | کل قرعه با `{}`؛ یا `{"weightCategory":"-58"}`؛ `type` اختیاری |
| `POST /tournaments/{id}/reset-category` | بازنشانی براکت و وزن‌کشی یک وزن، قبل از شروع بازی‌ها |
| `POST /tournaments/{id}/rebalance` | بازتخصیص زمین‌ها طبق تنظیمات، قبل از شروع |
| `GET /tournaments/{id}/draw-readiness` | آمادگی شماره‌گذاری |
| `POST /tournaments/{id}/numbering/preview` | پیش‌نمایش |
| `POST /tournaments/{id}/numbering` | ثبت شماره‌ها |
| `POST .../matches/{match}/start` | شروع بازی |
| `POST .../matches/{match}/result` | ثبت نتیجه و صعود برنده |
| `DELETE .../matches/{match}/result` | حذف نتیجه، فقط وقتی مراحل بعد هنوز شروع نشده‌اند |
| `PUT .../matches/{match}/number` | اصلاح شمارهٔ یک بازی پس از تکمیل همهٔ قرعه‌ها |
| `POST .../matches/{match}/move` | جابه‌جایی به جای خالی معتبر؛ `court,order` |

مسیر امضا فعلاً مرجع را ذخیره می‌کند؛ انتقال فایل محلی Rust به فضای ذخیره‌سازی وب هنوز انجام نشده است. جابه‌جایی دستی صف، مثل اپ بازچینی خودکار همهٔ جایگاه‌ها نیست؛ جای اشغال‌شده یا نقض تقدم براکت رد می‌شود.

در این مرحله عملیات مدیریتی تورنومنت برای `owner/organizer` و عملیات وزن‌کشی/نتیجه برای `owner/organizer/referee` است. دسترسی مربی/ورزشکار به درخواست ثبت‌نام و تأیید برگزارکننده، مرحلهٔ بعدی است.

## دیتابیس و مهاجرت

`000003` رکوردهای قبلی JSONB را به `tournament_entries` و `tournament_matches` منتقل می‌کند. هر ثبت‌نام و بازی ردیف مستقل دارد؛ جزئیات راندها و snapshot در JSONB همان ردیف باقی می‌مانند. قفل تورنومنت، اعتبارسنجی، تغییر بازی‌ها و ثبت رویداد audit در یک تراکنش انجام می‌شوند. پاسخ موفق فقط پس از commit فرستاده می‌شود.

رکوردهای قبلی که سازمان ندارند عمداً به یک سازمان حدس‌زده‌شده واگذار نمی‌شوند. پیش از استفاده از دیتابیس قدیمی باید مالکیت آن‌ها تعیین شود. runner جدید برای دیتابیس تازه تست شده است؛ دیتابیس ساخته‌شده با اجرای دستی migrationهای قبلی نیاز به ثبت baseline مطابق schema واقعی دارد. هنوز انتقال داده‌های واقعی اپ یا دیتابیس موجود کاربر اجرا نشده است.

## تست‌ها

- تست‌های Go برای مرزهای وزن، تلاش‌ها، امضا، پروفایل، قفل‌ها، سیدبندی، استراحت، جداسازی باشگاه، امتیازدهی، سه روش چیدمان، دو روز و محدودهٔ شماره‌ها.
- fixture تولیدشده از کد واقعی TypeScript برای اوزان، نتایج راند و براکت‌های ۲، ۳، ۵، ۸ و ۱۶ نفره.
- تست API روی PostgreSQL: اجرای دوبارهٔ migration، ذخیره/بازیابی، جداسازی سازمان‌ها، rollback، `If-Match` قدیمی و شروع هم‌زمان روی یک زمین.
- ۱۱ تست Node برای منطق و store اپ، به‌علاوهٔ type-check و build Vue.

اجرا از پوشهٔ `backend`:

```powershell
go test ./...
go vet ./...
$env:TEST_DATABASE_URL='postgres://user:password@127.0.0.1:5432/testdb?sslmode=disable'
go test ./... -count=1
```

تست‌های PostgreSQL بدون `TEST_DATABASE_URL` skip می‌شوند. با آن، schema تصادفی جدا ساخته و فقط همان schema پاک می‌شود. تست‌های قدیمی Docker در `internal/database` با تگ `integration` نگه داشته شده‌اند و به Docker فعال نیاز دارند. Race detector در محیط فعلی به علت نبود CGO/compiler اجرا نشد؛ تست درخواست‌های هم‌زمان روی PostgreSQL اجرا شد.

از پوشهٔ اپ:

```powershell
npm test
npm run build
node tests/export-parity.mjs ../taekwondo_web/backend/internal/modules/tournaments/testdata/desktop-parity.json
```

پس از تغییر منطق مرجع، fixture را دوباره تولید کنید و تست Go را اجرا کنید؛ fixture را دستی مطابق پیاده‌سازی Go تغییر ندهید.
